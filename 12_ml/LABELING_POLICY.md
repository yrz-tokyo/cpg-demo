# ラベル付けの方針と、その出所

## このモデルが何をするのか（1文）

**検出器が出した「同名の数値列グループ」の行列を並べ替えて、スチュワードが上から見るだけで
本物の定義衝突に当たるようにする。** 新しい知見を発見する装置ではなく、**レビューの処理量を上げる装置**。

## 正直に書いておくこと

- **ラベルは私（構築者）がスチュワード役として付けた判断です。** 実在の業務担当者の合議ではありません。
  データが合成なので実在のスチュワードは存在しません。
- したがって評価が言えるのは「**保留したスチュワード判断を再現できるか**」まで。
  「衝突を発見する能力」ではありません。
- 判断は下の方針に沿って、**1グループずつコメントと実測値を読んで**付けます。
  機械的に一括適用はしません（例外は記録します）。

## 判断の方針

### label = 1（本物の衝突。正本を決める必要がある）

次を**両方**満たすとき。

1. **業務の言葉が同じになる。** 現場が同じ言葉（売上、原価、投下額…）で呼びうる
2. **意味が違う。** どちらを使うかで答えが業務的に変わる

典型:
- 同名の measure が**別部門**にあり、片方は売上で片方は仕入（`total_net_amount`）
- 同名だが**集計範囲が違う**（キャンペーン投下額 と 消費者調査費）
- 同名だが**universe が違う**（自社の店頭実売 と 市場全体）
- 同名だが**建値が違う**（USD と JPY）

### label = 0（衝突ではない。レビュー不要）

- **同じ列が core → mart に集計されただけ。** マートは core の集計なので同義。
  `cross_layer = 1` かつ関与部門が1つのものはほぼこれ
- **汎用的な名前が偶然一致しただけで、業務の言葉にならない。**
  `created_timestamp` 相当の数値列、`line_number`、`sequence` など
- **単位も universe も同じで、値が実質一致する。** 最大/最小比が 1.0 付近
- **技術的な補助列。** 行数カウント、ハッシュ、フラグの合計など業務で呼ばれない列

### 判断に使ってはいけないもの

- **`certified_count` を label の根拠にしない。** 認定は統治の**結果**であって原因ではない。
  認定済みだから衝突、という循環を作らない（特徴量としては使うが、ラベルの理由には書かない）
- **`max_over_min` だけで決めない。** 値が大きく違っても、単に粒度が違うだけのことがある。
  必ずコメントを読む

## 特徴量とラベルの関係について（弱点の明示）

特徴量（部門数・跨層・建値・コメント類似など）は、上の方針が参照する情報と**重なります**。
つまりモデルは「方針を新しい検出に適用する」ことを学びます。これは
learning-to-rank / トリアージ自動化としては普通の形ですが、
**「モデルが人間の知らない衝突を見つけた」という主張はできません**。

言えるのはこれだけです:

> 検出器は82グループを出す。全部人が見るのは現実的でない。
> モデルは保留したスチュワード判断を交差検証で再現できるので、
> 上位N件だけ見れば本物に当たる。次のレビューがラベルを増やし、次の並べ替えが良くなる。

## 評価の仕方

- **層化k分割交差検証**（ラベルが偏るため）
- 見るのは **PR-AUC と上位N件の適合率**。正答率は不均衡データで意味が薄い
- **ベースラインと比べる**: ①`max_over_min` 降順 ②`n_objects` 降順 ③ランダム
  モデルがこの3つに勝てなければ、モデルは不要という結論を書く
- すべて MLflow に記録し、UC に登録する
